# airecogn

D7-модуль Bitrix для обработки записей телефонных звонков, передачи аудио в Nextcloud, приёма результатов AI-распознавания, обновления CRM-активити и синхронизации данных с Oracle.

Текущая версия: `0.3.0`.

## Что делает модуль

- подписывается на внутреннее событие `voximplant:onCallEnd`;
- ставит обработку завершённого звонка в фоновую очередь Bitrix;
- находит запись звонка в Bitrix Disk;
- читает технический Voximplant-лог и извлекает маршрут переводов, операторов и временные метрики;
- сохраняет базовую информацию об активити в Oracle, если интеграция включена;
- пропускает записи длительностью меньше 11 секунд и звонки без сохранённого аудио;
- отправляет подходящий аудиофайл в Nextcloud по WebDAV;
- сохраняет локальный результат каждого найденного звонка;
- принимает итог распознавания через публичный inbound endpoint;
- обновляет описание и состояние CRM-активити;
- сохраняет итог в `b_airecogn_result` и Oracle;
- добавляет в карточку CRM-контакта вкладки с результатами и административными логами.

## Архитектура

```text
Voximplant
    │ voximplant:onCallEnd
    ▼
VoximplantEventHandler
    │ фоновая задача Bitrix
    ▼
EndCallProcessor
    ├── CRM-активити / статистика Voximplant / технический лог звонка
    ├── Oracle CRM_ACTIVITY + CRM_ACTIVITY_ROUTE
    ├── Bitrix Disk → Nextcloud WebDAV
    ├── b_airecogn_result: skipped_* / error / pending
    └── описание CRM-активити с итогом первичной обработки

Внешняя система распознавания
    │ POST JSON
    ▼
/local/handler/airecogn/inbound/index.php
    ▼
lib/http/inboundhandler.php
    ├── проверка контракта JSON
    ├── обновление описания CRM-активити
    ├── b_airecogn_result: success / error
    ├── Oracle CRM_ACTIVITY + CRM_ACTIVITY_QUESTION
    └── завершение CRM-активити при success

Карточка CRM-контакта
    ├── recognition.grid → b_airecogn_result JOIN b_crm_act_bind
    └── log.viewer → JSONL-файлы, фильтр по contact_id
```

## Обработка завершённого звонка

1. `VoximplantEventHandler` получает массив события Bitrix.
2. `CRM_ACTIVITY_ID` должен быть положительным целым числом либо строкой только из цифр. Значение один раз нормализуется в PHP `int`; дроби, знаки, пробелы, примесь других символов и переполнение считаются ошибкой.
3. Событие записывается в канал `end_call` и передаётся в `Application::addBackgroundJob()` с низким приоритетом.
4. `EndCallProcessor` загружает CRM-активити и конфигурацию. Отсутствие активити или некорректный ID завершает фоновую задачу с исключением.
5. Из активити берётся первый `STORAGE_ELEMENT_ID`, а из `Bitrix\Voximplant\StatisticTable` — URL технического лога, длительность и дата начала звонка.
6. Если записи нет, локально сохраняется `skipped_no_recording`, а в описание активити записывается соответствующий комментарий.
7. Если длительность записи меньше 11 секунд, локально сохраняется `skipped_short`, а в описание активити записывается существующая подсказка «Длительность разговора <10 сек. Расшифровке не подлежит.».
8. Если длительность определить не удалось либо обработка данных звонка завершилась исключением, локально сохраняется `error`. В описание активити записывается стандартный блок «Ошибка распознования. Обратитесь к администратору», затем `[B]Кратко:[/B]` и причина.
9. Для подходящей записи разбирается технический лог: маршрут переводов, первый и последний оператор, время до ответа и длительность переводов.
10. При включённом Oracle выполняется update-or-insert основной строки активити и обновляется маршрут переводов.
11. Файл из Bitrix Disk отправляется в Nextcloud методом WebDAV `PUT`.
12. После успешной загрузки создаётся локальная строка `pending`, а описание активити получает маркер `[AI_CALL_RECOGNISER_PENDING]`.
13. При ошибке подготовки файла или загрузки создаётся локальная строка `error`, а в описание активити записывается тот же стандартный блок ошибки с краткой причиной.

Если Oracle отключён, это считается штатным режимом и не записывается как ошибка. Ошибки Oracle логируются. Ошибки Nextcloud дополнительно сохраняются в локальной таблице и описании активити. Автоматического повтора сейчас нет.

## Inbound endpoint

Адрес:

```text
POST /local/handler/airecogn/inbound/index.php
Content-Type: application/json
```

Минимальный пакет:

```json
{
  "call_id": 412937,
  "call_status": "success",
  "summary": "Краткое содержание разговора",
  "questions": [
    {
      "id": 1,
      "text": "Клиент подтвердил обращение",
      "answer": "true"
    }
  ]
}
```

Контракт намеренно строгий:

- корнем должен быть JSON-объект;
- `call_id` — обязательное положительное целое число либо строка только из цифр; `412937`, `"412937"` и `"00412937"` равнозначны и нормализуются в `int`;
- `call_status` — только строка `success` или `error`;
- `summary` — обязательная строка;
- `questions`, если передан, — JSON-массив;
- каждый вопрос содержит положительный целый `id` либо его цифровую строковую запись, строковый `text` и строковый `answer` со значением `true` или `false`.

Для числовых идентификаторов не принимаются нулевое значение, отрицательные и дробные числа, строки со знаком, пробелами или другими символами, а также значения за пределами PHP `int`. Ведущие нули в цифровой строке допустимы и удаляются при нормализации.

Любой другой статус отклоняется с HTTP 400.

После проверки endpoint:

1. загружает CRM-активити;
2. определяет единственный связанный контакт;
3. заменяет маркер ожидания блоком результата либо полностью формирует описание;
4. сохраняет локальный результат;
5. обновляет существующую строку Oracle или создаёт полную строку, если её ещё нет;
6. заменяет вопросы в Oracle;
7. при `success` завершает CRM-активити;
8. возвращает `{"status":"ok","updated":true}`.

Повторный inbound для того же `call_id` обновляет существующую строку и не создаёт дубль.

### Важное ограничение безопасности

Inbound endpoint сейчас не имеет токена, подписи или фильтра по IP. Он доступен без авторизации Bitrix и доверяет источнику после проверки структуры JSON. До эксплуатации на публичном боевом портале необходимо добавить аутентификацию запроса. Рекомендуемый минимум — секретный Bearer-токен или HMAC-подпись, HTTPS и ограничение частоты запросов.

## Определение контакта

`ContactResolver` принимает ID CRM-активити:

1. если `OWNER_TYPE_ID === CCrmOwnerType::Contact`, используется `OWNER_ID`;
2. иначе выполняется один запрос в `b_crm_act_bind` по типу `Contact`;
3. отсутствие контактной привязки считается ошибкой;
4. результат кешируется в памяти до завершения текущего PHP-процесса.

Найденный ID:

- добавляется в новые JSONL-записи как `contact_id`;
- передаётся в Oracle `PBI_ABITURIENT.CRM_ACTIVITY.CONTACT_ID`;
- используется вкладкой логов для фильтрации без запросов к CRM.

## Локальная таблица результатов

Таблица `b_airecogn_result`:

| Поле | Назначение |
|---|---|
| `ID` | Первичный ключ |
| `ACTIVITY_ID` | Уникальный ID CRM-активити |
| `STATUS` | `pending`, `success`, `error`, `skipped_no_recording` или `skipped_short` |
| `SUMMARY` | Краткое содержание распознавания |
| `CREATED_AT` | Время создания строки |
| `UPDATED_AT` | Время последнего изменения |
| `PROCESSED_AT` | Время получения окончательного результата |

В таблице намеренно не хранятся вопросы, маршрут звонка и `CONTACT_ID`. Контакт для грида определяется SQL-соединением с `b_crm_act_bind`; вопросы и маршрут используются в описании CRM и Oracle.

## Oracle

Интеграция работает только при включённой опции и загруженном расширении OCI8.

Используемые таблицы:

- `PBI_ABITURIENT.CRM_ACTIVITY` — основная строка активити, распознавание, метрики, операторы, URL лога и `CONTACT_ID`;
- `PBI_ABITURIENT.CRM_ACTIVITY_ROUTE` — маршрут переводов;
- `PBI_ABITURIENT.CRM_ACTIVITY_QUESTION` — вопросы и ответы распознавания.

Основная строка сохраняется по схеме update-then-insert по `ACTIVITY_ID`. Первичная обработка передаёт в Oracle тот же итог, что сохраняется локально: `pending`, `error`, `skipped_short` или `skipped_no_recording`. Inbound обновляет статус, summary, контакт и вопросы. Для pending-обновления существующие итоговый статус и summary в Oracle не перезаписываются.

В Oracle должна существовать колонка `CRM_ACTIVITY.CONTACT_ID`. Модуль не создаёт и не изменяет Oracle-схему.

Ошибки Oracle попадают в JSONL-лог соответствующего канала. Отдельной очереди повторов и автоматического восстановления нет.

## Nextcloud

Аудио загружается по WebDAV `PUT` с Basic Auth.

Удалённый каталог строится по шаблону настройки, поддерживаются маркеры `{Y}`, `{m}`, `{d}`. Имя файла формируется как:

```text
<CRM_ACTIVITY_ID>_<STORAGE_ELEMENT_ID>.<extension>
```

Ограничения текущей реализации:

- удалённые каталоги не создаются через `MKCOL`, они должны существовать заранее;
- connect timeout — 10 секунд, общий timeout — 120 секунд;
- автоматического повтора загрузки нет;
- неудачная загрузка фиксируется статусом `error` в `b_airecogn_result` и комментарием в активити;
- при повторной обработке успешная загрузка переводит существующий `error` или `skipped_*` в `pending`, но не затирает готовый `success`;
- успешная отправка подтверждается любым HTTP-кодом 2xx.

## CRM-вкладки

Событие `crm:onEntityDetailsTabsInitialized` добавляет вкладки только в существующую карточку контакта:

- `Распознавание звонков` — доступна пользователям с правом чтения контакта;
- `Логи распознавания` — создаётся только для администраторов.

Параметры вкладок подписываются средствами CRM и проверяются в AJAX endpoint. `recognition.grid` фильтрует результаты одним SQL-запросом через JOIN с `b_crm_act_bind`, применяет пагинацию в базе и обновляет страницы через собственный `AJAX_LOADER`, не перезагружая карточку контакта.

`log.viewer` читает ограниченный хвост каналов `end_call` и `inbound`, оставляет строки с `contact_id` текущего контакта и сортирует их по времени. Старые строки без `contact_id` во вкладке не отображаются.

## Логи

Каталог:

```text
/local/logs/airecogn/
```

Каналы:

```text
end_call_YYYY-MM-DD.log
inbound_YYYY-MM-DD.log
```

Каждая строка — отдельный JSON-объект. Базовые поля:

```json
{
  "timestamp": "2026-07-22T10:00:00+07:00",
  "level": "info",
  "channel": "end_call",
  "contact_id": 9,
  "activity_id": 412937
}
```

Канал `end_call` использует три типа записей:

- `queued` — звонок поставлен в фоновую очередь; содержит только `activity_id`, `call_id` и сообщение;
- `result` — единственная итоговая запись обработки с фиксированными секциями `call`, `recording`, `nextcloud`, `persistence` и, только для статуса `error`, `error`;
- `fatal` — активити не удалось получить, поэтому итоговую запись сформировать невозможно.

Пойманные ошибки конфигурации, статистики, файла и Nextcloud не создают дополнительные строки: они входят в итоговый `result`. Ошибки сохранения локального результата, Oracle и описания активити находятся в секции `persistence` этой же записи.

Размер одного файла ограничен 5 МиБ. После заполнения создаются части:

```text
end_call_YYYY-MM-DD_001.log
end_call_YYYY-MM-DD_002.log
```

Запись сериализуется блокировкой канала. Одиночная запись больше 5 МиБ заменяется короткой диагностической записью. Просмотрщик читает файл с конца блоками по 64 КиБ и останавливается после достижения `log_tail_size`, поэтому весь файл в память не загружается.

Лимит применяется отдельно к каждому каналу: при `log_tail_size = 200` до фильтрации может быть прочитано до 200 строк `end_call` и до 200 строк `inbound`.

Ограничение 5 МиБ действует на каждую часть, но общего срока хранения и лимита каталога нет. Очистку старых файлов следует настроить отдельно.

## Настройки

Страница: `Настройки → Настройки продукта → Настройки модулей → airecogn`.

| Опция | Значение по умолчанию | Назначение |
|---|---:|---|
| `enabled` | `Y` | Включает обработчики модуля |
| `logging_enabled` | `Y` | Включает JSONL-логирование |
| `log_level` | `info` | Минимальный уровень: `debug`, `info`, `error` |
| `log_tail_size` | `200` | Строк на канал в просмотрщике, диапазон 10–2000 |
| `nextcloud_webdav_url` | пусто | Базовый WebDAV URL |
| `nextcloud_username` | пусто | Пользователь Nextcloud |
| `nextcloud_password` | пусто | Пароль Nextcloud |
| `nextcloud_remote_dir` | `/Calls/{Y}/{m}` | Шаблон удалённого каталога |
| `oracle_enabled` | `N` | Включает Oracle |
| `oracle_username` | пусто | Пользователь Oracle |
| `oracle_password` | пусто | Пароль Oracle |
| `oracle_connection_string` | пусто | Строка подключения OCI8 |
| `oracle_charset` | `AL32UTF8` | Кодировка Oracle |

Секреты хранятся стандартным механизмом опций Bitrix. Дополнительного шифрования на уровне модуля нет.

## Установка и обновление

1. Поместить каталог `airecogn` в `/local/modules`.
2. Установить модуль в административном разделе Bitrix.
3. Заполнить Nextcloud и при необходимости Oracle.
4. Убедиться, что удалённый каталог Nextcloud существует.
5. Настроить внешнюю систему на inbound endpoint.
6. До публикации endpoint добавить и согласовать аутентификацию.

Установка создаёт таблицу, регистрирует три события и копирует компоненты с публичными обработчиками. Если создание таблицы завершилось ошибкой, модуль не регистрируется.

Автоматического механизма миграций между версиями пока нет. Изменение `install.sql` не обновляет уже существующую таблицу.

## Диагностика

- Нет вкладок: проверить `enabled`, регистрацию `crm:onEntityDetailsTabsInitialized` и синхронизацию установленных компонентов.
- Пустой грид: проверить наличие строки в `b_airecogn_result` и контактной привязки активити в `b_crm_act_bind`.
- Пустая вкладка логов: запись должна находиться в читаемом хвосте и содержать `contact_id` текущего контакта.
- Нет pending: проверить строку `error`, описание активити и журнал `end_call`; pending создаётся только после успешной загрузки файла.
- Inbound возвращает 400: проверить формат идентификаторов; допустимы положительное JSON-целое или строка только из цифр.
- Inbound возвращает 500: проверить существование CRM-активити, единственную привязку контакта и журнал `inbound`.
- Oracle не обновляется: проверить `oracle_enabled`, OCI8, реквизиты, колонку `CONTACT_ID` и JSONL-ошибки.
- Nextcloud возвращает 404/409: обычно отсутствует один из удалённых каталогов.

## Рекомендации и известные ограничения

### Критично перед боевой эксплуатацией

1. Добавить аутентификацию inbound endpoint. Сейчас любой сетевой клиент, знающий ID активити, может попытаться изменить CRM и Oracle.
2. Не возвращать внешнему клиенту внутренний текст исключений после появления аутентификации; оставить подробности только в журнале.
3. Проверить наличие `CONTACT_ID` в Oracle до развёртывания версии `0.3.0`.

### Надёжность интеграций

1. Добавить персистентную очередь повторов для Nextcloud и Oracle. Сейчас автоматического повтора нет.
2. Создавать WebDAV-каталоги через `MKCOL` либо проверять их при сохранении настроек.
3. Добавить идемпотентный сценарий повторной отправки аудио.
4. Решить, должна ли ошибка Oracle приводить к неуспешному HTTP-ответу inbound. Сейчас CRM и локальная таблица могут обновиться, а Oracle — нет, после чего endpoint всё равно вернёт 200.

### Эксплуатация

1. Настроить удаление логов старше согласованного срока: ротация ограничивает часть файла, но не общий объём каталога.
2. Добавить мониторинг неуспешных фоновых задач Bitrix.
3. Проверить PHP timezone контейнера: дата имени лог-файла строится по серверному времени, а не по часовому поясу пользователя.
4. Добавить реальные интеграционные тесты Nextcloud и Oracle в отдельном защищённом окружении.

### Развитие кода

`legacy/functions.php` содержит несколько независимых областей: описание CRM, парсер Voximplant и Oracle. Пока код стабилен, дробить его только ради количества классов не нужно. При дальнейшем развитии разумная граница — три небольших сервиса по этим областям с сохранением текущих чистых функций парсинга.
